## How to Start

```powershell
cd botpy\examples
python client.py
```

`client.py` now pins the subprocess cwd to the examples directory, so it will not fail to find resources even when started from elsewhere;
but the cache files are still written under the cwd, so starting it as shown above is still recommended.

## Key Constraint: Paths Depend on the Current Working Directory

The three rendering scripts read and write data and resources through paths relative to the cwd, so **the directory structure must not be moved around arbitrarily**:

| Relative path | Used by | Description |
|---|---|---|
| `mtr_pathfinder_data` | `mtr_*` | Root directory of icons and fonts |
| `mtr_pathfinder_temp` | Same as above | Temporary .dat, recreated automatically if it does not exist |
| `chat_bot.db` | `plugins/fortune_by_sqlite.py` | Already changed to an absolute path based on the file location |
| `mtr-original-data-*.json` / `mtr-route-departure-*.json` | `mtr_timetable.py`, `mtr_diagram.py`, v4 | Network data cache, stored in the cwd |

## Logging

All logs (this program + botpy internals) are written uniformly to **`botpy/examples/logs/bot.log`**,
UTF-8, default single file 5 MB, keeping 5 rotation backups. `botpy.log` is no longer produced separately.

### Format and Request Tracing

```
2026-11-17 22:31:02 INFO    [a1b2c3d4] mtrqqbot.client client.py:65 执行外部脚本 script=mtr_timetable.py args=('7号线', ...)
2026-11-17 22:31:02 INFO    [a1b2c3d4] mtrqqbot.client client.py:99 脚本结束 script=mtr_timetable.py rc=0 耗时=84ms stdout=63B stderr=0B
2026-11-17 22:31:02 INFO    [a1b2c3d4] mtrqqbot.client client.py:159 准备上传图片 file=mtrqqbot_timetable_x.png 原始=93KB base64=124KB
2026-11-17 22:31:03 INFO    [a1b2c3d4] mtrqqbot.client client.py:197 发送图片返回 status=200 总耗时=812ms
2026-11-17 22:31:03 INFO    [a1b2c3d4] mtrqqbot.client client.py:250 消息处理结束 耗时=1204ms
```

The part in `[...]` is the **request id** (taken from the last 8 digits of the QQ message id); one command's
"receive message → run script → upload → finish" all carry the same id, so a complete chain can be grepped out directly:

```powershell
Select-String -Path botpy\examples\logs\bot.log -Pattern 'a1b2c3d4'
```

The request id is stored with `contextvars`, so concurrent triggers from multiple groups do not get mixed up.

### Environment Variables

| Variable | Default | Description |
|---|---|---|
| `MTR_LOG_DIR` | `botpy/examples/logs` | Log directory |
| `MTR_LOG_LEVEL` | `INFO` | Level written to the file; `DEBUG` records the scripts' complete stdout/stderr and exception tracebacks |
| `MTR_LOG_CONSOLE` | `WARNING` | Console level. **The default of WARNING is intentional**: the scripts' stderr is what the client uses to judge failure, and INFO would pollute it |
| `MTR_LOG_MAX_BYTES` | `5242880` | Maximum size per file |
| `MTR_LOG_BACKUPS` | `5` | Number of rotation backups |

When troubleshooting:

```powershell
$env:MTR_LOG_LEVEL='DEBUG'      # 把脚本完整输出、HTTP 响应体、异常堆栈都写进日志
$env:MTR_LOG_CONSOLE='INFO'     # 同时让出图脚本把自己的诊断信息打到 stderr
cd botpy\examples
python client.py
```

Running a script alone and wanting to see diagnostic information:

```powershell
cd botpy\examples
$env:MTR_LOG_CONSOLE='INFO'
python mtr_timetable.py "7号线" --output C:\tmp\tt.png
```

### Design Trade-offs

- **Failure to create the log file will not bring the bot down**: when the directory is not writable it degrades automatically to console-only output and writes one warning.
- **`print` is kept**: the rendering scripts' `SUCCESS:<路径>` / `FAILED` is the machine contract by which the client judges success or failure, and cannot be changed to logging (it would go to stderr and the contract would break). The scripts' diagnostic information goes through logging and is not output at the default level.
- **Messages sent back to QQ are still truncated to 300 characters**, but the complete original text goes into the log at DEBUG level, so there is evidence when something goes wrong.

## This Round's Code Fix List

### Issues That Made Features Completely Unusable

| File | Problem | Fix |
|---|---|---|
| `client.py` | `cmd = ['py', ...]` invoked the py launcher, which by default points to Python 3.15, whereas the bot runs on 3.8 with completely different dependencies → every command failed | Switched to `sys.executable` (can be overridden with `MTR_PYTHON`) |
| `client.py` | The subprocess outputs Chinese in GBK, but it was decoded with `encoding='utf-8'` → `UnicodeDecodeError`, swallowed as "系统执行出错", **every `/go` necessarily failed** | Force `PYTHONIOENCODING/PYTHONUTF8` in the subprocess environment, and add `errors='replace'` to the decoding |
| `mtr_pathfinder_v4.py` | Used 55 occurrences of `dict[...]`/`list[...]` built-in generic annotations without `from __future__`, so on Python 3.8 the import itself raised `TypeError: 'type' object is not subscriptable` | Added `from __future__ import annotations` |
| `raqm_support.py` | `libraqm.dll` never took effect: Pillow finds it through an ordinary `LoadLibrary`, which only succeeds when the cwd happens to be examples; rendering from any other directory raised `not supported without libraqm` | Added a module that preloads both DLLs with `ctypes` by absolute path; testing showed `add_dll_directory` does not work and `PATH` works but pollutes the environment, hence the preload approach |
| `mtr_timetable.py`<br>`mtr_diagram.py` | Dwell time was read from `route.get('dwellTime')`, but that field actually hangs on **each station** (90 routes have 0 route-level fields, all 371 stations have it) → dwell time was always 0, and the timetable's "arrival/departure" were forever merged into one line | Read uniformly from stations via `mtr_data.station_dwells()`, while remaining compatible with the old route-level arrays |
| `mtr_timetable.py` | The header took `stations[i]['name']`, which is the **index within the route** ("1", "2", …) → the whole header was "站 1" | Changed to look up `data['stations'][id]['name']` to get the real station name |
| `plugins/user_todo_list.py` | The directory was hard-coded as `'..\\examples\\user_data\\'`, which resolved to a nonexistent path when started from examples → all to-do features hit `FileNotFoundError` | Computed from `__file__`, can be overridden with `MTR_USER_DATA_DIR`, and the directory is created automatically before reading/writing |
| `plugins/fortune_by_sqlite.py` | `from sqlalchemy.orm import declarative_base` raised ImportError on SQLAlchemy 1.3 (this machine has 1.3.18) → the module could not be imported at all | Compatible with both import paths |
| `plugins/fortune_by_sqlite.py` | `class QrFortune:` did not inherit from `Base` and was not a real model | Changed to inherit from `Base` |
| `plugins/web_screen_shot.py` | **Importing the module started Chrome**, and without selenium installed it raised ImportError outright | Changed to a functional style with zero import side effects, importing selenium lazily only when called |
| `user_data/__init__.py` | `os.listdir('')` raised `FileNotFoundError` outright; and it would treat **every** file in the directory (including itself) as JSON and overwrite it | Locate via `__file__`, and only handle `*.json` |

### Robustness and Correctness

| File | Problem | Fix |
|---|---|---|
| `client.py` | `subprocess.run` executed synchronously, so the whole bot hung and did not respond to other messages during pathfinding | Moved it into a thread pool (`run_in_executor`) so the event loop is not blocked |
| `client.py` | Temporary images were written to the cwd, cleanup on exception paths was incomplete, and subprocesses had no timeout | Written to the system temporary directory, cleaned up uniformly in `finally`, with a 180-second timeout |
| `client.py` | `/go` was matched with `startswith`, so `/google` was also treated as a pathfinding command | Command table + word-boundary matching (`bot_commands.match_command`) |
| `client.py` | A missing `config['appid']` key raised KeyError, making it impossible to tell it was a configuration problem | Validated at startup, with a readable Chinese prompt when it is missing |
| `client.py` | The 40 lines of subprocess logic were copied once for each of the three commands | Extracted into `bot_commands` + `_generate_and_send` |
| `client.py` | aiohttp requests had no timeout | Added a uniform `ClientTimeout(total=60)` |
| `mtr_timetable.py`<br>`mtr_diagram.py` | `IndexError` when `durations` was shorter than the number of stations; formatting crashed when `route['color']` was not an integer | Treat missing entries as 0; added a gray fallback in `hex_color()` |
| `mtr_diagram.py` | The station order of reverse routes (`CW` / `Back`) is the reverse of the base route, while the code "truncated as soon as the index decreased", so the whole route was cut down to 1~2 stations and a steep, useless line was drawn on the diagram (measured: `CW Back` left with only 1 station, `CW` with only 2 stations, total duration 129 seconds vs. the normal 1277 seconds) | First determine the direction from the first/last index, flip the station order and `durations` back together, and only then truncate; trains with fewer than 2 stations are skipped entirely |
| `mtr_pathfinder_v4.py` | Every pathfinding run forcibly fetched data from `http://localhost:1025` and threw an exception on failure — **even when the local cache was intact** — so `/go` became entirely unavailable as soon as the map service stopped | Automatically fall back to the local cache when fetching fails (station names and departure data judged separately), failing honestly only when even the cache is missing; the fallback is recorded at INFO level and does not pollute stderr |
| `mtr_diagram.py` | Degenerate routes such as single-station loops (e.g. `Y01` has only 2 stations and both are "森川") reported "no departure times found", which did not match the real cause | Distinguish the two failures "abnormal station-order data (fewer than 2 valid stations)" and "no departure times" |
| `mtr_diagram.py` | When several trains departed close together, the "local / express" labels piled up into a blob (you could see "普普普" on the diagram) | Record the x-coordinate of each drawn label and skip when the spacing is under 16px |
| `mtr_timetable.py`<br>`mtr_diagram.py`<br>`mtr_pathfinder_v4.py` | Still exited 0 on failure, so the script caller could not tell | Unified `SystemExit(1)` on failure for the three scripts |
| `plugins/user_todo_list.py` | Older versions wrote `[占位, ' ']` when creating the file, and that space consumed an index; `delete()` reset the whole table when the list had ≤2 items | Filter out blank entries on read; `delete()` really deletes a single entry and writes a placeholder only when the list becomes empty |
| `plugins/user_todo_list.py` | `json.dump` defaulted to `ensure_ascii=True`, and `open()` did not specify an encoding | Unified UTF-8 + `ensure_ascii=False`; sanitize path separators in file names |
| `plugins/img_upload.py` | A missing `config['picturesToken']` key raised KeyError; when an upload failed `res['data']` was None → AttributeError; file handles were not closed; `delete_img()` raised NameError when nothing had been uploaded; requests had no timeout | Fully reworked: readable errors, `success` judgement, `with open`, explicit error from `delete_img(url=None)`, `timeout=30` |
| `plugins/weather_api.py` | Chinese city names were spliced into the URL without encoding; hard indexing with `data['reason']`; requests had no timeout | Switched to `params` so requests does the encoding; all `.get()`; `timeout=15`; the API Key supports the `JUHE_WEATHER_KEY` environment variable |
| `plugins/fortune_by_sqlite.py` | The DB path `sqlite:///./chat_bot.db` was relative to the cwd; duplicate detection used `date('now')` (UTC, so before 8 a.m. in UTC+8 it counts as yesterday); `"python"` was hard-coded; `None.fortune_summary` crashed when the table was empty; `echo=True` flooded the output | Absolute path; `date('now','localtime')`; `sys.executable`; automatic initialization with a fallback error when the table is empty; `echo=False` |
| `fortune_init_data.py` | `sqlite3.connect('chat_bot.db')` was relative to the cwd and would create a second, empty database | Based on `__file__` |
| `mtr_pathfinder_v4.py` | A duplicated `import argparse` was left in the middle of the file | Removed |
| Logging (whole project) | All logs were crammed into `botpy.log` in the cwd: no rotation, mixed together with botpy internal logs, no request identifier; the three scripts used `print` throughout, so diagnostic information existed only in stdout truncated to 300 characters | Added `logging_setup.py`: unified UTF-8 rotating files, `[reqid]` throughout one command, configurable level/directory/size via environment variables, automatic degradation when the log directory is not writable; the scripts switched to logging but **kept** the stdout `SUCCESS`/`FAILED` contract |

## Known Issues (Still Need Your Action)

1. **`config.yaml` is missing `picturesToken`**: `plugins/img_upload.py` is still the only reader, and a missing key now produces a clear prompt (no longer a KeyError). To fill it in, go to the sm.ms backend under User → Dashboard → API Token, copy the Secret Token, and paste it there.
2. **`config.yaml` contains a real `appid` and `secret`**, and it is already excluded by `.gitignore`. When adding it to a repository later, do not force-commit it with `git add -f`; once it leaks, reset it on the QQ Open Platform.
3. **The aggregated-data API Key in `plugins/weather_api.py` was hard-coded publicly in the source by the original author**; it is recommended to reset it in the backend and switch to the `JUHE_WEATHER_KEY` environment variable.
4. **The plugin layer is not referenced by `client.py`**: `plugins/` and `user_data/` are code left over from the official botpy examples, and this bot's actual functionality all lives in `client.py` + the three `mtr_*.py` scripts. This code has been fixed but is still in a "usable library" state; wiring it into commands is up to you.

## Tests

```powershell
cd MTRPathQQBot-main
python -B tests\run_all.py
```

Currently **all 112 tests pass**, finishing in about 30 seconds. It uses the standard library `unittest` and does not depend on pytest.

Coverage:

| File | What it covers |
|---|---|
| `tests/test_bot_commands.py` | Command recognition (including the regression test that `/google` must not match `/go`), `--no-xxx` parameter stripping, `起点;终点` parsing, the command line having to use the current interpreter rather than `py`, the UTF-8 subprocess environment, `SUCCESS`/`FAILED` judgement of script output |
| `tests/test_mtr_data.py` | Uses real cache data to assert "dwell time lives on stations, not at route level", plus arrival-departure offsets, fallback for missing data, and color parsing |
| `tests/test_plugins.py` | To-do add/delete/update/query and index semantics, the readable error when the image host token is missing, weather formatting fault tolerance, no import side effects from the screenshot module, the fortune model being registered and using the local time zone |
| `tests/test_render.py` | **Really runs** `mtr_timetable.py` / `mtr_diagram.py` / `mtr_pathfinder_v4.py`, asserting the exit code, the `SUCCESS` output, and that the artifact is a valid PNG; there is also one test verifying raqm works under a "foreign cwd"; it also includes source-code constraint checks for `client.py` |
| `tests/test_logging.py` | Log persistence and UTF-8, line-prefix format including file name and line number, levels and `MTR_LOG_LEVEL`/`MTR_LOG_CONSOLE`, injection/isolation/restoration of the request id, repeated `setup()` not producing duplicate lines, size-based rotation and backup limits, degradation when the log directory is not writable, the start/end/exception paths of the `traced` decorator; in addition it **really runs** `script_runner.run_script` once to invoke a rendering script, asserting that the lines "execute / finish (rc=0, elapsed) / non-zero exit" all land on disk and that complete stdout is retained at DEBUG level |
| `tests/test_client_flow.py` | Uses botpy/aiohttp stand-ins to really run `client.py`: text commands such as `/ping` `/jam`, `/google` not triggering `/go`, `/go` semicolon/same-station/empty-station/usage validation, parameter pass-through of `--no-highspeed` and `--no-线路名`, the full `/时刻表` chain (really render a PNG → fake upload → assert the base64 is a PNG), the upload-failure branch, and graceful failure of `/go` when there is no data source |

The tests copy the cache data and `mtr_pathfinder_data` into a temporary working directory to run (the scripts use paths relative to the cwd), and clean up automatically afterwards.

**What cannot be tested in this environment** (requires a real environment):

- Real message sending/receiving in a QQ group, and the image host upload of `send_base64_image` — requires `qq-botpy` and valid credentials;
- The network fetching paths of `fetch_data` / `gen_departure` — requires a local MTR map service (`http://localhost:1025`); the offline tests go through the `--no-update` cache branch;
- The selenium-related features under `plugins/` — this machine does not have selenium / chromedriver installed.
